One resource. The whole Pulse stack.

The Pulse operator installs the agent, the console and PostgreSQL from a single OpenShiftPulse resource, then keeps them matching it. Change a field and the cluster follows; turn a component off and it is removed.

Everything it manages

The operator owns the whole lifecycle of a Pulse installation: install, upgrade, isolation, recovery and removal.

Install and upgrade

A real OpenShift operator, through OLM.

  • Shows up in Installed Operators and upgrades itself from its catalog
  • Every release publishes a bundle and a catalog with the full upgrade path
  • Rolls the agent and console as a matched pair of images
  • Optional version floor: an incompatible operator pins the agent instead of rolling it

Heal itself

Fixes its own installation and tells you it did.

  • Replaces agent and console pods stuck pending, failing to pull, or crash-looping
  • Recovers a PostgreSQL pod stuck pending
  • Puts back a Route or a sign-in cookie secret that someone changed
  • Adopts an installation that was previously managed by Helm

Sign-in and permissions

Least privilege, with the switches in one place.

  • OpenShift sign-in through an OAuth proxy and its own OAuthClient
  • The agent reads; writes and Secret access are separate opt-ins
  • Name the admins who may edit skills and approve monitor fixes
  • The operator itself holds no escalate or bind rights

Data that survives

Deleting Pulse does not delete what it learned.

  • PostgreSQL as a StatefulSet on its own volume
  • The data volume and database password are kept on delete
  • Reinstall and the agent picks up its history, memory and skills
  • Temporal's databases live in the same instance when enabled

Observability

Status you can read from the resource itself.

  • Phase and per-component readiness on the resource, plus the Route it serves
  • Operator metrics: self-heal actions, readiness, reconcile errors by step
  • Observed against requested memory, to size each component
  • A ServiceMonitor and alerts for when the agent or database is down

Knows your cluster

Configures itself from what is already there.

  • Finds the cluster's application domain for the Route
  • Uses the OAuth proxy image that matches your OpenShift version
  • Detects Advanced Cluster Management for multi-cluster features
  • Names cluster-wide objects per namespace, so installations never collide

Who can reach what

Each component gets a network policy for what may connect to it. Outgoing traffic is not restricted, so metrics, logs, sign-in and the Claude API keep working.

What's new

v0.11.022 October 2026
Pairs with agent and UI v2.34.0
No CRD or RBAC changes

  • The database is actually isolated. The PostgreSQL network policy selected no pods, so any pod could reach it. It now admits only the agent and, when enabled, Temporal. This starts applying when you upgrade.
  • Turning something off removes it. Disabling MCP, Temporal or the Temporal UI deletes what was created for it, instead of leaving it running with its permissions in place.
  • Works on bare metal, vSphere and single-node clusters. The console now admits routers running on the host network, the default there, which previously got a 503.
  • Cleaner deletes and a patched toolchain. Deleting the resource no longer hangs where the OpenShift OAuth API is missing, never removes another installation's objects, and the operator is built with Go 1.26.10 for a crypto/x509 advisory.

Install

Needs OpenShift 4.12 or later. Installing through OLM puts Pulse in Installed Operators and gives it automatic upgrades.

  1. Add the catalog

    Create the pulse-operator-catalog CatalogSource in openshift-marketplace.

  2. Make a namespace

    oc new-project openshiftpulse, then create the Secret for your Claude backend there.

  3. Subscribe

    Create an OperatorGroup and a Subscription to the operator.

  4. Create Pulse

    Apply an OpenShiftPulse resource like the one above, and open the Route it reports.
